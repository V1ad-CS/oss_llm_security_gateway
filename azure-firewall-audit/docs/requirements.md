# Требования к инструменту аудита конфигурации Azure Firewall и NSG

Версия документа 1.2 · ноябрь 2026 · соответствует azure-firewall-audit 1.2.0

Документ задаёт требования к инструменту `azfw_audit.py` из каталога `azure-firewall-audit/`
репозитория oss_llm_security_gateway: что инструмент должен делать, какие ограничения
безопасности соблюдать, в каком окружении работать и как проверяется выполнение требований.
Устройство инструмента и порядок эксплуатации описаны в отдельном документе
«Описание решения и руководство администратора» (`docs/description.md`).

## 1. Общие сведения

### 1.1. Назначение

Инструмент периодически получает конфигурацию сетевой защиты в Microsoft Azure — Azure Firewall
и Network Security Groups (NSG), — сравнивает её с предыдущим сбором и с утверждённым эталоном,
проверяет на соответствие стандарту безопасности организации, формирует три отчёта и сообщает
об ошибках в Rocket.Chat.

Инструмент решает четыре задачи:

1. **Контроль изменений.** Выявить, что изменилось с прошлого сбора и чем конфигурация
   отличается от утверждённого эталона: какие правила добавлены, удалены, переименованы или
   изменены, и кто вносил изменения.
2. **Контроль соответствия.** Выявить нарушения стандарта ИБ: опасные правила (доступ «любой →
   любой», открытые для Интернета RDP и SSH), слабые режимы защиты, отсутствие журналирования.
3. **Отчётность.** Сформировать для специалистов по ИБ, аудиторов и конвейеров три отчёта:
   «Изменения с прошлого сбора», «Отличия от эталона» и «Нарушения стандарта ИБ».
4. **Оповещение.** Сообщить в Rocket.Chat, если проверка не выполнена или данные неполные, а по
   настройке — и о превышении порогов.

Инструмент **не изменяет** конфигурацию Azure. Устранение нарушений и откат изменений выполняют
люди по процессу управления изменениями.

### 1.2. Область применения

| Объект | Что входит |
|------------------|---------------------------------------------------------------|
| Azure Firewall | Все уровни SKU (Basic, Standard, Premium), брандмауэры в виртуальной сети и в защищённом концентраторе Virtual WAN; классические правила |
| Azure Firewall Policy | Политики брандмауэров, цепочки базовых политик, группы коллекций правил, в том числе из других подписок |
| IP Groups | IP-группы, на которые ссылаются правила и настройки обхода IDPS |
| Network Security Groups | Пользовательские правила, привязки к подсетям и сетевым интерфейсам |
| Параметры диагностики | Отправка журналов Azure Firewall в Log Analytics, хранилище, Event Hub |
| Журнал действий Azure | Операции изменения перечисленных объектов и подсетей |
| Rocket.Chat | Сообщения во входящий вебхук (интеграция Incoming WebHook) |
| Облака Azure | Глобальное облако и национальные облака (через адрес Resource Manager) |

### 1.3. Вне рамок

- Изменение конфигурации Azure, автоматическое исправление нарушений и откат.
- Анализ сетевого трафика и содержимого журналов брандмауэра.
- Виртуальные сети, таблицы маршрутов, Azure Firewall Manager, маршрутизация Virtual WAN.
- Вычисление эффективных правил NSG для сочетания «NSG подсети + NSG сетевого интерфейса».
- Межсетевые экраны сторонних производителей (NVA).
- Непрерывный мониторинг в реальном времени: инструмент запускается по расписанию или вручную.

### 1.4. Термины и сокращения

| Термин | Определение |
|------------------|---------------------------------------------------------------|
| ARM | Azure Resource Manager — API управления ресурсами Azure |
| ASG | Application Security Group — группа безопасности приложений |
| IaC | Infrastructure as Code — описание инфраструктуры шаблонами (Bicep, Terraform и т. п.) |
| NSG | Network Security Group — группа безопасности сети |
| RBAC | Ролевое управление доступом Azure |
| Снимок | JSON-файл с конфигурацией, полученной из Azure в определённый момент |
| Предыдущий снимок | Снимок предыдущего запуска; с ним сравнивается текущий снимок в отчёте 1 |
| Эталон | Утверждённый снимок, с которым сравнивается текущий снимок в отчёте 2 |
| Изменение | Различие между двумя снимками (drift) |
| Отклонение, нарушение | Несоответствие конфигурации стандарту (finding) |
| Вебхук | Адрес входящей интеграции Rocket.Chat вида `https://<сервер>/hooks/<id>/<токен>`; токен в адресе — секрет |
| Стандарт | Файл `standard.yaml` с требованиями к конфигурации |
| Исключение | Согласованное отклонение с обоснованием и, при необходимости, сроком действия |
| Доступ из Интернета | Входящее разрешающее правило NSG с источником `*`, `0.0.0.0/0` или `Internet` |

## 2. Пользователи и сценарии использования

### 2.1. Роли

| Роль | Задачи | Что получает |
|------------------|---------------------------------------------------------------|----------------------|
| Администратор сети | Утверждает эталон после согласованных изменений, устраняет отклонения | Отчёты 1 и 2, снимки |
| Специалист ИБ | Разбирает нарушения и несогласованные изменения, согласует исключения | Отчёты 2 и 3, журнал действий |
| Аудитор | Подтверждает соответствие конфигурации стандарту на дату | Отчёт 3 в HTML или Markdown, снимок |
| Дежурная смена | Реагирует на сбои регулярной проверки | Сообщения в Rocket.Chat |
| Конвейер CI/CD | Запускает проверку по расписанию, останавливается при нарушениях | Код выхода, отчёты в JSON |

### 2.2. Сценарии

| № | Сценарий | Команда |
|------|----------------------------------------------------------------------|------------|
| С1 | Создать эталон: собрать конфигурацию, проверить отчёт по ней, утвердить и сохранить снимок | `collect`, `report` |
| С2 | Регулярная проверка: собрать снимок, сравнить с предыдущим и с эталоном, проверить по стандарту, сохранить три отчёта, сообщить результат кодом выхода | `run` |
| С3 | Разбор инцидента: выяснить, какие правила изменились и кто их менял | `run` (журнал действий) |
| С4 | Повторный отчёт по сохранённым снимкам без доступа к Azure, например для аудитора или с изменённым стандартом | `report` |
| С5 | Проверка до и после окна изменений: снимок до работ становится эталоном, после работ — сравнивается с ним | `collect`, `run` |
| С6 | Оповещение: регулярная проверка не выполнилась или прочитала не всё — дежурная смена получает сообщение в Rocket.Chat | `run` |

## 3. Функциональные требования

Приоритет: **О** — обязательное требование, **Ж** — желательное. Как проверяется каждое
требование — автоматическим тестом из `tests/test_azfw_audit.py` или вручную, — показано в
приложении Б.

### 3.1. Сбор конфигурации

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-COL-01 | Получать все Azure Firewall в подписке, в группе ресурсов или только с указанными именами | О |
| FR-COL-02 | Получать классические коллекции правил брандмауэра: сетевые, правил приложений, NAT | О |
| FR-COL-03 | Получать Firewall Policy каждого брандмауэра и всю цепочку базовых политик, в том числе из других подписок | О |
| FR-COL-04 | Получать все группы коллекций правил каждой политики | О |
| FR-COL-05 | По отдельному параметру получать все политики области, включая не привязанные к брандмауэрам | Ж |
| FR-COL-06 | Получать IP-группы, на которые ссылаются правила и настройки обхода IDPS | О |
| FR-COL-07 | Получать параметры диагностики каждого брандмауэра; давать возможность отключить их чтение | О |
| FR-COL-08 | Получать все NSG области с пользовательскими правилами и привязками к подсетям и сетевым интерфейсам; давать возможность ограничить их список именами или отключить чтение | О |
| FR-COL-09 | По заданной глубине (не более 90 дней) получать из журнала действий завершённые операции изменения брандмауэров, политик, IP-групп, NSG, подсетей и параметров диагностики брандмауэров | О |
| FR-COL-10 | Работать с несколькими подписками, в том числе со всеми доступными учётной записи | О |
| FR-COL-11 | Получать все страницы постраничных ответов ARM (`nextLink`) | О |
| FR-COL-12 | Сохранять снимок в JSON с временем сбора, областью сбора, версиями API и списком ошибок | О |
| FR-COL-13 | Ошибка чтения отдельного объекта не должна прерывать сбор: ошибка записывается в снимок с признаком неполноты данных. Ответ 404 означает отсутствие объекта и неполнотой не считается | О |

### 3.2. Выявление изменений

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-DRF-01 | Сравнивать текущий снимок с предыдущим снимком и с эталоном по отдельным объектам: брандмауэр, политика, группа коллекций, коллекция, правило, IP-группа, параметр диагностики, NSG, правило NSG | О |
| FR-DRF-02 | Относить каждое различие к одному виду: добавлено, удалено, изменено, переименовано. Переименованием считается правило с тем же содержимым и новым именем в той же коллекции или NSG | О |
| FR-DRF-03 | Для изменённых объектов показывать изменённые поля со старым и новым значением, для списков — добавленные и удалённые элементы | О |
| FR-DRF-04 | Не считать изменением: служебные поля (`etag`, `provisioningState`, `size`, `changeNumber`), обратные ссылки, которые ведёт Azure, порядок элементов списков, регистр ARM ID, различие пустого и отсутствующего значения | О |
| FR-DRF-05 | Для NSG не считать изменением правила по умолчанию, запись значения в единственном или множественном поле (`destinationPortRange` / `destinationPortRanges` и аналогичные), появление и исчезновение сетевых интерфейсов экземпляров масштабируемых наборов | О |
| FR-DRF-06 | Сравнивать привязки NSG к подсетям и сетевым интерфейсам; отвязку NSG от подсети показывать как изменение | О |
| FR-DRF-07 | Объект, который не удалось прочитать (кроме ответа 404), показывать как «не сравнивался», а не как удалённый или добавленный. Ошибка получения списка объектов одного типа не должна влиять на сравнение объектов других типов | О |
| FR-DRF-08 | Раздел, который не собирался в одном из снимков (NSG, параметры диагностики), не сравнивать и отмечать это в отчёте | О |
| FR-DRF-09 | Предупреждать, если область сбора снимка, с которым сравнивают, и текущего снимка различается | Ж |
| FR-DRF-10 | Находить предыдущий снимок автоматически: самый новый читаемый `azfw-snapshot-*.json` в каталоге результатов; повреждённые снимки пропускать с предупреждением; позволять указать снимок явно | О |

### 3.3. Проверка по стандарту

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-CHK-01 | Читать требования из YAML-файла стандарта; отсутствующие параметры брать из значений по умолчанию; при неверных значениях завершаться с ошибкой и не формировать отчёт | О |
| FR-CHK-02 | Проверять настройки брандмауэров: состояние развёртывания, уровень SKU, режим Threat Intelligence с учётом цепочки базовых политик, режим IDPS и TLS-инспекцию (Premium), DNS proxy при FQDN в сетевых правилах, отправку журналов, зоны доступности, использование классических правил | О |
| FR-CHK-03 | Проверять правила Azure Firewall: «любой → любой», все порты или слишком широкий диапазон, протокол Any, чувствительные порты для любого источника (включая порт после трансляции DNAT), публикацию DNAT вне разрешённых портов, `*` и шаблоны доменной зоны верхнего уровня в правилах приложений, дубли правил, пустые коллекции, отсутствие описания | О |
| FR-CHK-04 | При проверке источников учитывать содержимое IP-групп: адрес `0.0.0.0/0` в IP-группе означает «любой источник» | О |
| FR-CHK-05 | Проверять NSG: входящие разрешающие правила, открывающие для Интернета все порты, чувствительные порты, слишком широкий диапазон или порт вне списка разрешённых; NSG без привязок | О |
| FR-CHK-06 | Для NSG вычитать порты, которые закрывает запрещающее правило с более высоким приоритетом для того же протокола, источников из Интернета и тех же назначений | О |
| FR-CHK-07 | Проверять произвольные ожидаемые значения свойств брандмауэров, политик и NSG, заданные в стандарте путями в JSON ресурса | О |
| FR-CHK-08 | Для каждого отклонения указывать идентификатор проверки, уровень (критический, высокий, средний, низкий, инфо), объект (путь вида `группа ресурсов/ресурс/…/правило`), описание, рекомендацию и устойчивый отпечаток для систем мониторинга | О |
| FR-CHK-09 | Перечень проверок и их уровни — по приложению А | О |

### 3.4. Исключения

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-EXC-01 | Задавать исключения в стандарте: проверка (шаблон с `*` и `?`), объект (шаблон), обоснование (обязательно), срок действия (необязательно); сравнение без учёта регистра | О |
| FR-EXC-02 | Выводить принятые отклонения отдельным разделом отчёта с обоснованием и сроком; не учитывать их в порогах кода выхода | О |
| FR-EXC-03 | Не применять исключения без обоснования и с истёкшим сроком и сообщать о них в отчёте; сообщать об исключениях, которые не совпали ни с одним отклонением | О |

### 3.5. Отчёты

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-REP-01 | Формировать три отдельных отчёта: 1 — «Изменения с прошлого сбора» (текущий снимок против предыдущего), 2 — «Отличия от эталона» (против эталона), 3 — «Нарушения стандарта ИБ» (по стандарту) | О |
| FR-REP-02 | Каждый отчёт формировать в форматах Markdown, HTML и JSON, по выбору — в одном или нескольких | О |
| FR-REP-03 | HTML-отчёт должен быть одним файлом без внешних ресурсов, читаться в светлой и тёмной теме и на экране телефона | Ж |
| FR-REP-04 | Отчёты 1 и 2 содержат: итог, таблицу изменений, объекты, которые не сравнивались, журнал действий за период после снимка, с которым сравнивают, ошибки получения данных. Если снимка для сравнения нет, отчёт объясняет почему | О |
| FR-REP-05 | Отчёт 3 содержит: итог, нарушения по убыванию уровня, рекомендации, исключения, инвентаризацию (брандмауэры, политики, NSG), ошибки получения данных | О |
| FR-REP-06 | Отчёты формируются по сохранённым снимкам без обращения к Azure; можно выбрать отдельные отчёты | О |
| FR-REP-07 | Язык отчётов, справки командной строки и сообщений — русский | О |

### 3.6. Запуск и интеграция

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-CLI-01 | Предоставлять команды `collect` (снимок), `report` (отчёты по снимкам) и `run` (снимок и три отчёта за один запуск) | О |
| FR-CLI-02 | Завершаться с кодом 0 — норма, 1 — ошибка, 2 — превышены пороги, 3 — часть конфигурации не прочитана | О |
| FR-CLI-03 | Задавать пороги: минимальный уровень нарушений (`--fail-on`), наличие отличий от эталона (`--fail-on-drift`) и изменений с прошлого сбора (`--fail-on-change`) | О |
| FR-CLI-04 | В команде `run` по умолчанию читать журнал действий с даты самого старого из сравниваемых снимков, но не более чем за 90 дней | Ж |
| FR-CLI-05 | Называть файлы снимка и отчётов по виду отчёта и времени сбора снимка: `azfw-snapshot-<время>.json`, `azfw-changes-<время>.*`, `azfw-drift-<время>.*`, `azfw-compliance-<время>.*` | О |

### 3.7. Уведомления в Rocket.Chat

| ID | Требование | Пр. |
|--------------|-------------------------------------------------------------------------------------|-------|
| FR-NOT-01 | Отправлять сообщение во входящий вебхук Rocket.Chat, если запуск не выполнен (код 1), в том числе при непредвиденном сбое, и если часть конфигурации не прочитана (код 3) | О |
| FR-NOT-02 | По настройке отправлять сообщение также при превышении порогов (код 2) или после каждого запуска | О |
| FR-NOT-03 | Сообщение содержит статус, команду, код выхода, узел, область сбора, текст ошибки или список непрочитанных объектов с подсказкой, итоги трёх отчётов, до пяти самых серьёзных нарушений, сработавшие пороги и имена файлов отчётов; длина сообщения ограничена | О |
| FR-NOT-04 | Сбой отправки не меняет код выхода; при ответах 429, 5xx и сетевых ошибках отправка повторяется, всего до 3 попыток | О |
| FR-NOT-05 | Адрес вебхука задаётся переменной окружения или параметром командной строки; без адреса уведомления не отправляются | О |

## 4. Требования информационной безопасности

| ID | Требование |
|------------|------------------------------------------------------------------------------------------|
| SEC-01 | **Только чтение.** Отправлять в Azure Resource Manager только GET-запросы. Единственный запрос не на чтение — POST сообщения во вебхук Rocket.Chat; он выполняется отдельной HTTP-сессией и только на адрес вебхука. Транспортный уровень HTTP-клиента должен блокировать POST, PUT, PATCH и DELETE до отправки, даже при ошибке в коде. Не использовать POST-операции, которые только читают данные (`listIdpsSignatures`, `learnedIPPrefixes`) |
| SEC-02 | **Минимальные права.** Работать со встроенной ролью Reader; не требовать ролей с правом записи |
| SEC-03 | **Защита токена.** Отправлять токен доступа только на адрес Resource Manager; отклонять ссылки на следующую страницу (`nextLink`) с другим адресом |
| SEC-04 | **Учётные данные.** Не хранить учётные данные в коде, снимках и отчётах. Получать токен через `azure-identity`: переменные окружения, управляемое удостоверение, workload identity, `az login` |
| SEC-05 | **Отказ входа.** При невозможности получить токен завершаться с кодом 1, не формируя отчёт |

| Назначение | Адрес | Порт |

внутреннего центра сертификации для Rocket.Chat — через `REQUESTS_CA_BUNDLE`.

### 6.3. Учётная запись и права

| Что читается | Право | Встроенная роль |
|----------------------------------|----------------------------------------|----------------|
| Брандмауэры, политики, группы правил, IP-группы, NSG | `Microsoft.Network/*/read` | Reader |
| Параметры диагностики | `Microsoft.Insights/diagnosticSettings/read` | Reader |
| Журнал действий | `Microsoft.Insights/eventtypes/values/read` | Reader |
| Список подписок (`--all-subscriptions`) | доступ к подпискам | Reader |

Роль назначается на каждую подписку или группу ресурсов, где находятся брандмауэры, политики
(включая базовые), IP-группы и NSG. Учётная запись — сервисный принципал, управляемое
удостоверение или учётная запись пользователя; для запуска по расписанию рекомендуется
управляемое удостоверение или workload identity (OIDC), чтобы не хранить секрет.

### 6.4. Хранилище

- Каталог для снимков и отчётов с доступом только для администраторов сети, ИБ и аудиторов. Он
  должен сохраняться между запусками: в нём ищется предыдущий снимок для отчёта 1. Каждый запуск
  добавляет снимок и до девяти файлов отчётов, поэтому нужен регламент очистки.
- Место для эталона с историей изменений и ревью (репозиторий git).
- Объём: снимок занимает десятки килобайт на брандмауэр или NSG; отчёты — того же порядка.

### 6.5. Rocket.Chat

- Входящая интеграция (Incoming WebHook) в канале оповещений; права администратора Rocket.Chat
  нужны только для её создания.
- Сетевой доступ к серверу Rocket.Chat с узла, где запускается инструмент.

## 9. Допущения и ограничения

- Конфигурация описана в IaC или иным способом позволяет откатить несогласованное изменение;
  инструмент только обнаруживает такие изменения.
- Каталог результатов сохраняется между запусками; если его очистить, следующий отчёт 1 сообщит,
  что предыдущий снимок не найден.
- Rocket.Chat доступен с узла запуска; если нет, уведомление теряется, а результат проверки
  остаётся в коде выхода и отчётах.
- Журнал действий Azure хранит события 90 дней; более ранние изменения видны только как
  различие снимков, без автора.
- В Azure Firewall не анализируется затенение правил коллекциями с более высоким приоритетом;
  выявляются только точные дубли.
- Сервисные теги и FQDN-теги Azure Firewall не раскрываются; `Internet` и `AzureCloud` не
  считаются «любым адресом» для правил брандмауэра. Для NSG тег `Internet` означает доступ из
  Интернета.
- Каждая NSG проверяется отдельно; состав групп безопасности приложений не раскрывается.
- Виртуальные сети не читаются, поэтому подсети без NSG не выявляются; журналы потоков (flow
  logs) не проверяются.
- Черновики политик (`firewallPolicyDrafts`) не читаются.
